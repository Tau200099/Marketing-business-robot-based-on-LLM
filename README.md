# 飞书群关键词机器人

监听飞书群消息（**文字 + 图片**），识别销售报单后以「引用回复」的形式自动点赞。

- **接收方式**：WebSocket 长连接 —— 不需要公网 IP、不需要域名备案、不需要内网穿透，本地起进程即可
- **两层判断**：确定性关键词规则本地秒回；规则没命中的，粗筛后交给模型判断意图并生成回复
- **响应速度**：规则层 200–400ms；模型层 1–3 秒（只有粗筛命中的消息才会走到这层）
- **成本控制**：群里大部分闲聊在本地粗筛就被丢掉，不产生 API 调用；另有每分钟调用上限做费用刹车
- **图片识别**：本地 OCR 读受理单截图，图片不外传，单张约 1.15 秒（见第七节）
- **清单与通报**：晒单自动记进活动台账，按小组/战队汇总排名，定点 + 跟单发「文字 + 表格图 + Excel」（见第十一节）

---

## 一、先搞清楚一件事

飞书里的**「自定义机器人」（群 Webhook）只能发消息，收不到任何群消息**。它没有事件订阅能力。

要「识别群消息 → 匹配 → 回复」，必须建**企业自建应用**并开启机器人能力。本项目走的就是这条路。它加进群之后的样子和自定义机器人一样，但底层完全不同。

## 二、飞书开放平台配置

飞书后台 UI 时有调整，以下是路径大意，按名称找即可。

### 1. 创建应用

访问 <https://open.feishu.cn/app> → **创建企业自建应用** → 填名称和图标。

创建后在**「凭证与基础信息」**里拿到 `App ID` 和 `App Secret`，待会儿要填进 `.env`。

### 2. 开启机器人能力

左侧**「添加应用能力」** → 找到**「机器人」** → 启用。

不开这个，后面的事件订阅拿不到消息。

### 3. 申请权限 ⚠️ 关键步骤

左侧**「权限管理」**，搜索并申请：

| 权限 | 用途 | 审批难度 |
|---|---|---|
| `im:message.group_msg` | **接收群里所有消息** | ⚠️ 高级权限，需管理员审批 |
| `im:message:send_as_bot` | 以机器人身份发消息 | 普通 |
| `im:message.p2p_msg:readonly` | 接收单聊消息（可选） | 普通 |
| `im:resource` | 下载消息里的图片 / 文件（OCR、名册 Excel 都靠它） | 普通 |
| `im:chat:readonly` | 查群成员姓名（清单里「揽收人」的兜底来源），以及 `diagnose.py` 列群 | 普通 |
| `contact:user.base:readonly` | 群成员里查不到时退到通讯录查姓名（可选） | 普通 |

**关于 `im:message.group_msg`：**

这是本项目当前配置（`require_at: false`，监听全部群消息）的**硬性前提**。

- 它属于**高级权限**，申请后需要企业管理员在管理后台审批，部分企业还要求填写用途说明或走报备流程
- **没批下来之前，飞书根本不会把「非 @ 机器人」的消息推给你** —— 程序不会报错，日志也是干净的，表现就是「机器人对群里的话毫无反应」。这是最容易误判成代码 bug 的地方

**如果审批一时下不来**，可以先降级跑通链路：申请 `im:message.group_at_msg:readonly`（申请即批，只能收到 @ 机器人的消息），然后把 `config.yaml` 里改回：

```yaml
global:
  require_at: true
```

@ 一下机器人验证全链路通了，等权限批下来再改回 `false`。

### 4. 配置事件订阅

左侧**「事件与回调」→「事件配置」**：

1. 订阅方式选**「使用长连接接收事件」**
   —— **不要**选「将事件发送至开发者服务器」，那个需要公网回调地址
2. 添加事件：**`im.message.receive_v1`**（接收消息）

选了长连接之后，`Encrypt Key` / `Verification Token` 就用不上了，代码里对应参数留空。

### 5. 发布应用

左侧**「版本管理与发布」** → 创建版本 → 填可用范围 → 申请发布 → 等管理员审批通过。

### 6. 把机器人拉进群

目标群 → **群设置 → 群机器人 → 添加机器人** → 选你刚发布的应用。

## 三、本地运行

### 建虚拟环境 + 装依赖

**不要直接 `pip install` 装进全局 / Anaconda base 环境**，会污染其它项目。先建项目独立的虚拟环境：

```bash
python -m venv .venv
```

然后激活（按你用的终端选一条）：

```powershell
.venv\Scripts\Activate.ps1
```

```bash
source .venv/Scripts/activate
```

> PowerShell 若报「禁止运行脚本」，执行一次
> `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` 即可；
> 或者干脆用 cmd 的 `.venv\Scripts\activate.bat`。

激活后命令行前面会出现 `(.venv)`。此时装依赖：

```bash
pip install -r requirements.txt
```

之后所有命令都在**激活状态下**跑。也可以不激活，直接用 venv 里的解释器：

```bash
.venv\Scripts\python.exe bot.py
```

`.venv/` 已在 `.gitignore` 里，不会被提交。

> 你如果习惯用 conda，`conda create -n feishu_bot python=3.11` 再
> `conda activate feishu_bot` 同样可以，别用 base 就行。

### 填凭证

把 `.env.example` 复制成 `.env`，填入第 2 步拿到的凭证：

```
FEISHU_APP_ID=cli_xxxxxxxxxxxxxxxx
FEISHU_APP_SECRET=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
LOG_LEVEL=INFO
```

`.env` 已在 `.gitignore` 里，不会被提交。

### 先离线测路由（不需要凭证、不联网、不花钱）

```bash
python test_rules.py
```

测某一句话会走哪条路：

```bash
python test_rules.py "今天新增199一个"
```

批量测真实消息，这是调 `prefilter` 的正确姿势：

```bash
python test_rules.py --file messages.txt
```

### 启动

```bash
python bot.py
```

看到 `正在建立长连接……` 就是起来了。

### 首次上线：先自检

`config.yaml` 里默认**只开启一条规则「链路自检」**，触发词是 `机器人自检` —— 故意选了没人平时会说的词，保证首次上线群里零噪音。

其余都是示例规则，默认 `enabled: false`。**当前是全量监听（`require_at: false`），一旦开启，群里任何人说到那些词机器人都会接话**，正式用时请直接删掉换成你自己的规则。

上线后在群里发一句：

```
机器人自检
```

收到回复，说明**权限、长连接、事件订阅、回复接口**整条链路全通。日志里会打出命中的规则和端到端耗时。

没反应的话看最后一节排查表——最常见的是 `im:message.group_msg` 权限还没批下来。

## 四、配规则

全部规则在 [`config.yaml`](config.yaml)，改完存盘即生效（默认 5 秒检查一次，无需重启）。

### 三种匹配模式

```yaml
rules:
  # any —— 任意一个关键词出现就命中
  - name: 打招呼
    mode: any
    keywords: ["你好", "在吗", "hello", "hi"]
    reply: "在的，有什么可以帮你？"

  # all —— 全部关键词都出现才命中（适合减少误触发）
  - name: 报障升级
    mode: all
    keywords: ["生产", "故障"]
    reply: "已记录生产故障，正在通知值班同学。"
    at_sender: true      # 回复时 @ 触发者
    cooldown: 0          # 这条不限流

  # regex —— 当作正则，任一匹配即命中
  # 注意：正则必须用单引号！YAML 双引号会把 \d 当非法转义直接报错
  - name: 订单号识别
    mode: regex
    keywords: ['\bORD-\d{8,}\b', '订单号[:：]\s*\d+']
    reply: "收到订单号，正在查询中……"
```

### 排除词：挡掉「词对了但语境不对」

`任一` 模式只看词出现没出现，不看上下文。关键词配了「宽带」，群里说「宽带坏了报下障」照样会触发。

给规则加 `exclude`，**命中任意一个排除词就直接否决**（优先级高于 `keywords`）：

```yaml
  - name: 业绩点赞
    mode: any
    keywords: ["79", "99", "智屏", "宽带", "云盒"]
    exclude: ["?", "？", "怎么", "坏", "断", "报障", "退", "%"]
    reply: "点赞！！！👍👍"
```

效果：

| 消息 | 结果 |
|---|---|
| `宽带装好了` | ✅ 点赞 |
| `宽带坏了报下障` | ❌ 被 `坏` 否决 |
| `宽带什么时候能装` | ❌ 被 `？`/`什么时候` 否决 |
| `完成率79%` | ❌ 被 `%` 否决 |

排除词对 `regex` 模式同样生效。

> 实践经验：**问号是最好用的排除词**。报业绩、报单都是陈述句，带问号的基本是咨询和报修。

### 关键词边界（已自动处理）

子串匹配会误伤，`word_boundary` 默认 `auto`，按关键词类型自动选策略：

| 关键词类型 | 策略 | 效果 |
|---|---|---|
| **纯数字**（`79`） | 前后不能是数字 | `79元`✅ `新增79`✅ `179`❌ `1799`❌ |
| **纯英文**（`hi`） | 词边界 `\b` | `hi 大家`✅ `this`❌ `shipping`❌ |
| **含中文**（`宽带`） | 子串匹配 | `宽带装好了`✅ |

⚠️ **纯数字为什么不能用 `\b`**：Python 正则里**中文算单词字符**，`79元` 的 `9` 和 `元` 之间没有词边界，`\b79\b` 匹配不上——而这恰恰是中文群里最常见的写法。所以数字走的是「前后不能是数字」这个语义。

一般不用动它。特殊情况可按规则覆盖：

- `always` —— 一律加词边界（这样「你好」就匹配不到「你好啊」了）
- `never` —— 一律子串匹配（数字和英文关键词容易误伤，慎用）

### 全局开关

| 配置 | 说明 |
|---|---|
| `require_at` | `false` = 监听全部群消息（需 `im:message.group_msg` 权限）；`true` = 只回 @ 它的 |
| `enable_group` / `enable_p2p` | 分别控制是否响应群聊 / 单聊 |
| `ignore_self` | **务必保持 `true`**，见下方「防死循环」 |
| `default_cooldown` | 同一规则在同一会话的最小触发间隔，默认 10 秒 |
| `match_strategy` | `first` = 命中多条只回第一条；`all` = 每条都回 |
| `hot_reload` | 配置文件检查间隔（秒），`0` 关闭 |

## 五、两个必须知道的安全机制

### 防死循环

机器人自己发的消息同样会触发事件。不挡就是「回复 → 触发 → 再回复」的无限刷屏。

代码里做了双保险：过滤掉非真人发送者（`sender_type != "user"`，顺带挡掉其它机器人），再比对自身 `open_id`。**不要关掉 `ignore_self`。**

### 防刷屏

按 **（规则 × 会话）** 维度限流。同一条规则在同一个群里，`cooldown` 秒内只会触发一次；换个群互不影响。

全量监听模式下这个尤其重要 —— 群里反复出现关键词时，没有冷却机器人会一直回。

  platforms/            ← 只有这一层是平台相关的

    feishu.py           飞书：WebSocket 长连接，收发文字/图片/文件，查群成员姓名（已跑通）

**加一个平台 = 实现 `platforms/base.py` 那几个方法**，业务层一行都不用改。
可选方法不实现也行，业务层用 `hasattr` 判断，对应功能自动跳过。

### 响应速度是怎么保证的

1. **长连接** —— 事件直达，省掉 HTTP 回调的解析和 TLS 握手
2. **匹配零阻塞** —— 正则在启动时编译好，每条消息只做子串 / 正则扫描
3. **发送异步化** —— 事件回调里不等 HTTP 返回，立刻 `return`，否则 SDK 事件循环会被卡住导致后续消息排队
4. **token 自动缓存** —— SDK 内部管理 `tenant_access_token`，不会每次重新换取
5. **事件去重** —— 飞书会重推事件，按 `message_id` 幂等，固定容量 O(1)

日志里会打端到端耗时（收到事件 → 回复发出），实际数字直接可见。

## 七、图片 OCR

业务内容在受理单截图里，所以这层是**必需的**——关掉之后图片消息会被当成空文本直接丢弃，机器人对所有截图完全无反应，而且日志里看不到。

### ⚠️ 提纯是隐私闸门，不要绕过

现场照片可能拍到客户身份证、手机号——实测样本里就出现过：

```
...177xxxxxxxx ... 中华人民共和国 ... 居民身份证 ...
签发机关xx县公安局 有效期限20xx.xx.xx-20xx.xx.xx ...
```

OCR 会一视同仁地把这些识别出来。所以 `distill.py` 在 OCR 之后、送模型之前做两件事：

1. **抽取**「工作内容」字段，其余全部丢弃
2. **兜底脱敏**：手机号、身份证号、防伪码一律抹掉

实测效果（5 张真实现场照）：

| OCR 原文 | 提纯后 |
|---|---|
| 329 字（含身份证、手机号） | `工作内容：139改169+Fttr+2` |
| 137 字 | `工作内容：预约上门，新增149融合` |

一举三得：**证件信息发不出去、模型判断准了、token 省了 90%**。

### 全程本地，图片不外传

RapidOCR + onnxruntime，离线跑、不需要 GPU、不联网。**图片本身绝不上传任何地方**，只有识别出来的文本才会往下走到模型那一层。

### 实测性能

i5-9300H，560×400 的受理单截图：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 加载模型 | ~1.4 秒 | 启动时一次性付掉（`bot.py` 会预热） |
| 第一张图 | ~2.2 秒 | onnxruntime 首次按输入形状优化 |
| 之后每张 | ~1.15 秒 | 稳态 |

识别质量（同一张图）：

```
业务受理成功 受理单号：2024081500371 业务类型：宽带新装
套餐名称：融合套餐199元/月 合约期限：2 24个月 受理状态：受理成功 ...
```

套餐档位、受理状态这些关键字段都准确。偶有小瑕疵（上例「合约期限：2 24个月」多了个 2），不影响判断——`agent.context` 里已经告诉模型「OCR 可能有错字断行，别因为文本不通顺就判定不是报单」。

### 配置

```yaml
ocr:
  enabled: true
  max_chars: 500      # 识别文本截断，整张受理单可能几百字，全给模型既贵又淹没重点
  min_score: 0.5      # 低于此置信度的行丢掉，减少噪声
  max_images: 3       # 一条消息最多处理几张，防止一次发几十张把进程拖住
```

### 依赖版本坑

`requirements.txt` 里 `onnxruntime` 锁了 `>=1.19,<1.20`，**不要解锁**。

实测 `onnxruntime 1.29.0` 在 Windows 10 上导入即崩：

```
ImportError: DLL load failed while importing onnxruntime_pybind11_state
```

已排除两个常见原因——机器有 VC++ 14.40 运行库，CPU（i5-9300H）也支持 AVX2。是该版本自身的问题，`1.19.2` 实测正常。

### 线程模型

OCR 要 1 秒级，**绝不能在事件回调线程里跑**——会阻塞 SDK 事件循环，导致后续消息全部排队，一条慢消息拖垮整个群。

所以 `handler.py` 里分成两段：

- **事件回调线程**：去重 + 几个布尔判断，全是微秒级，做完立刻返回
- **线程池**：OCR、模型调用、发送请求

图片消息的完整耗时约 **1.2 秒 OCR + 1~3 秒模型 ≈ 3 秒**。点赞场景可以接受。

## 八、模型判断（agent）

### 为什么要这一层

纯关键词方案有两个治不好的毛病：

- **打地鼠**：关键词配了「宽带」，「宽带坏了报下障」也会触发。只能靠排除词一个个补，今天挡了「坏」，明天有人说「用不了」「装了半天没成」
- **顺序耦合**：「业绩新增」必须排在「业绩点赞」前面，否则 `新增79` 被点赞规则先吃掉。加第三条规则又得重新想插哪

这两件事的本质是同一个：**判断这条消息到底是「报单」还是「报障/咨询/闲聊」**。字符串匹配做不好，模型做得很好。

### 两层结构

```
群消息
   ↓
第一层 rules ── 确定性关键词，本地匹配，微秒级，零成本
   ↓ 命中 → 秒回，结束
   ↓ 没命中
第二层 agent
   ↓
   prefilter 粗筛（本地，零成本）
   ↓ 没命中 → 丢弃          ← 群里大部分闲聊在这里结束，不花一分钱
   ↓ 命中
   模型判断（一次调用，~1 秒）
   ↓ 不是报单 → 丢弃
   ↓ 是报单
   引用回复 + @ 报单人
```

**关键点：粗筛要宽，不要在这层做精细过滤。** 宁可多筛进来让模型判断——精细判断正是模型的活。粗筛只负责挡掉「明显无关」的消息，把成本压住。

### 配置

```yaml
agent:
  enabled: true
  base_url: https://api.deepseek.com
  model: deepseek-chat
  api_key_env: LLM_API_KEY      # 从环境变量读，不写在配置文件里

  timeout: 8
  temperature: 0.8              # 高一点让回复措辞有变化
  at_sender: true
  max_calls_per_minute: 60      # 费用刹车，超出跳过

  on_error: skip                # 模型不可用时：skip 不回 / fallback 用兜底话术
  fallback_reply: "点赞！！！👍👍"

  prefilter: ["79", "99", "智屏", "宽带", "云盒", "新增", "办理"]

  context: |
    （业务背景，会拼进系统提示词。写清楚场景、套餐档位、
      哪些说法算报单、哪些不算。模型判断会准很多。）
```

`on_error` 默认 `skip` 是刻意的：**漏回一条业绩，好过给报障消息回一句「点赞」。**

### 换服务商

国内几家都提供 OpenAI 兼容接口，只改两行，代码不动：

| 服务商 | `base_url` | `model` |
|---|---|---|
| DeepSeek | `https://api.deepseek.com` | `deepseek-chat` |
| 豆包·方舟 | `https://ark.cn-beijing.volces.com/api/v3` | 你的推理接入点 ID |
| 通义·百炼 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 智谱 | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-flash` |

⚠️ `base_url` 和 `model` 必须配套，换服务商两个都要改。

### 成本预估

只有粗筛命中的消息才调模型。看你的成本敞口有多大：

```bash
python test_rules.py
```

输出会标出每句话走哪条路，末尾给出比例：

```
  [规则] 机器人自检     ← 本地秒回，零成本
  [模型] 新增199        ← 会调一次模型
  [丢弃] 中午吃什么      ← 零成本

22 条里有 15 条会调模型（68%），其余零成本
```

真实群里闲聊占多数，实际比例会比这个样例低得多。

### 回退

模型效果不理想、或者 API 出问题想临时顶一下：把 `agent.enabled` 改成 `false`，同时把 `config.yaml` 里那两条停用的关键词规则 `enabled` 改回 `true`。存盘 5 秒内生效，不用重启。

## 九、支局战报

每来一单**新增**，在基础点赞之后追发一条战报并 @ 报单人：

```
① @他  新增139，漂亮！🎉👏
② @他  恭喜万盛支局新增宽带破"1"、新增中高套破"0"！👍👍👍👍
```

### 两个计数器

按 **（当天日期 × 支局）** 累计：

| 计数 | 规则 |
|---|---|
| `broadband` 新增宽带数 | **主宽算 1 个，每个副宽再各算 1 个** |
| `high` 新增中高套数 | 档位 **139 及以上**的算，副宽没有独立档位不计 |

**中高套定义**（在 `agent.context` 里，改政策改那儿）：

- **中套**：139、149、169
- **高套**：199、239、299、399
- 79、99 **不算**中高套

关键例子：

| 工作内容 | 宽带 | 中高套 | 说明 |
|---|---|---|---|
| `新增199+副宽` | **+2** | **+1** | 主宽+副宽两条宽带，但只有一个套餐 |
| `新增199+2个副宽` | +3 | +1 | |
| `新增副宽` | +1 | 0 | 没有独立档位 |
| `新增139+10` | +1 | +1 | `+10` 是附加项不是副宽 |
| `新增99` | +1 | 0 | 低于 139 |
| `199续约FTTR` | 0 | 0 | 不是新增 |
| `139改169` | 0 | 0 | 升档不是新增 |

**这两个数由模型数，不是代码里正则数的**——「+副宽」「带个副宽」「2个副宽」写法太多，正则数不准。模型返回 `broadband_count` 和 `high_count` 两个字段，`tally.py` 只负责累加和落盘。

**只有新增计数。** 续约、续签、升档、纯预约都不计——它们仍然有基础点赞，只是不发战报。

一天的实际效果（万盛支局）：

```
新增99        → 宽带破"1"、中高套破"0"
新增139+10    → 宽带破"2"、中高套破"1"
新增199+副宽   → 宽带破"4"、中高套破"2"      ← 宽带 +2
199续约FTTR   → （不发，不是新增）
新增副宽       → 宽带破"5"、中高套破"2"
```

### 支局从哪来

从照片水印里正则提取（`支局：万盛支局`）。**提不到就跳过战报**并打日志——播一条没有支局名的战报没意义，还会让那个支局的计数对不上。

实测 5 张真实照片，4 张能提到；提不到的那张是拍纸质文件的，水印被遮住了。

### 配置

```yaml
tally:
  enabled: true
  state_file: tally.json     # 计数落盘位置
  template: '恭喜{branch}新增宽带破"{broadband}"、新增中高套破"{high}"！👍👍👍👍'
```

中高套的档位范围**不在这里**，在 `agent.context` 的「中高套定义」那一段——它是喂给模型的业务背景，模型据此数 `high_count`。

模板三个占位符：`{branch}` 支局名、`{broadband}` 宽带数、`{high}` 中高套数。

### 计数会落盘

存 `tally.json`，**重启、断网、关机都不丢**。播一个错的数字比不播更难看——群里的人当场就能发现对不上。

写入用「先写临时文件再替换」，避免写一半崩了留下坏文件。

**跨天自动清零**，不需要定时任务：状态文件里存了日期，启动或记账时发现不是今天就直接重置。

## 十、重复内容检测

有人把同一张工作照重发一遍，战报数字就被刷上去了，统计就失去意义。所以加了这道。

### 判重依据

**水印时间 + 工作内容，两者都一致才算重复。**

只用时间会误伤——两个人恰好同一分钟拍照是有可能的。加上工作内容之后，实际撞车概率极低。

| 场景 | 判定 |
|---|---|
| 同时间 + 同工作内容 | ⚠️ 重复 |
| 同时间，不同工作内容 | 放行 |
| 同工作内容，不同时间 | 放行 |
| 时间抽不到 | 放行（没法判，会打日志） |
| 纯文字消息 | 放行（没有水印时间） |

### 命中之后

**不计入战报、也不发基础点赞**，只发一条警告并 @ 发送者：

```
⚠️ 这条和今天发过的重复了（水印时间 2026-08-22 16:37），本单不计入统计。
   如果确实是新单，请重新拍照上传。
```

判重范围是**全群**，指纹存在 `tally.json` 里，跟战报计数一起跨天清零。

### 配置

```yaml
dedupe:
  enabled: true
  template: "⚠️ 这条和今天发过的重复了（水印时间 {stamp}），本单不计入统计。如果确实是新单，请重新拍照上传。"
```

### ⚠️ 时间字段对分辨率敏感

水印里的时间字号很小，**缩图缩太狠会糊掉**，直接导致判不了重。实测 5 张真实照片：

| `ocr.max_side` | 时间提取成功 | 耗时 |
|---|---|---|
| 1280 | **3/5** | 3.4 秒/张 |
| **1600**（当前） | **5/5** | 4.4 秒/张 |
| 1920 / 不缩图 | 5/5 | 4.1–4.5 秒/张 |

**不要把 `max_side` 调到 1600 以下**，省下的 1 秒会换来判重失效。

### 两种水印模板都支持

```
时间：2026.08.22 16:37        ← 日期时间挨着（有的没空格：2026.08.2219:12）
打卡20:13 ... 2026.08.22星期六  ← 日期和时间在图上分开摆
```

第二种靠「打卡」附近的时钟 + 全文里的日期拼出来。

> 时间提取跑在**脱敏之后**——否则会抓到身份证的「有效期限20xx.xx.xx」当成水印时间。


## 十一、清单、晒单数据与通报

这一层把群里的晒单变成那张手工 Excel，再按时段发到群里。

### 数据流

```
群消息 ——【只有固定格式的文字晒单】（「业务晒单时刻」模板）才记单
    ↓ 照片和口语报单：点赞、表情包、战报照常，但不进清单、不触发跟单通报
    ↓ 同一单贴两遍（业务号码相同）会合并，不计两次
campaign.json（每单一行：新增/存量/单C、套餐、揽收人、各项计数、积分）
    ↓ 揽收人 → roster.json → 小组 / 战队
按小组求和 → 战队合计 → 综合进度 → 排名
    ↓
文字通报 + 表格 PNG + Excel（「晒单数据」+「清单」两张表）
```

综合进度 = 新增宽带/8×25% + 中高套/4×30% + 云盒AI智屏/5×15% + 积分/1000×20%。
目标值和权重在 `config.yaml` 的 `campaign.targets` 里，和原表 `晒单数据!W2` 的公式一致。

### 统计周期

```yaml
campaign:
  title: 城区营销活动
  rank_period: day        # 通报里的排名、晒单数据表、表格图：按天，每天重新比
  ledger_period: week     # Excel 里的「清单」：按周，本周一到周日的单都在一张表里
  start: ""               # 两个周期都可改成 fixed，用 start/end 指定几天（临时活动）
  end: ""
```

排名和清单分开算：**排名按天**（昨天冲得猛今天也不能躺），**清单按周**（周一自动翻页）。
`campaign.json` 里的历史单一直都在，只是出表和排名按周期切。

### 通报什么时候发

| 触发 | 发到哪 | 规则 |
|---|---|---|
| 跟单 | 晒单所在的群 | 有新单入清单就发，**一小时最多一次**。间隔没到的记着，一到就补发 |
| 定点 | `.env` 里 `FEISHU_CHAT_IDS` 的群 | `11:50` / `21:00`，是固定的，不看前面发没发过 |
| 命令 | 喊话的那个群 | 群里发「通报」「看排名」「清单」，立刻发一份 |

每次发三样：一段文字（前两名恭喜、末两名加油）、一张表格图、一个 Excel。
哪几样要发、话术怎么写，都在 `config.yaml` 的 `bulletin` 段。生成的文件落在 `reports/`。

改完话术或目标值，先离线看一眼再让机器人发：

```bash
python test_bulletin.py 2026-09-11 2026-09-14
```

### 群里 @机器人 问业绩（问答助手）

```
@机器人 今天各战队情况          @机器人 杨桐这周多少分
@机器人 哪些组还没晒单          @机器人 东林今天办了哪些单
@机器人 发一下通报
```

模型带着六个查台账的工具（战队汇总 / 小组汇总 / 个人明细 / 最近的单 / 名册 / 发通报）去答，
**所有数字来自代码算好的台账**，模型只负责听懂问题和组织语言。
只有 @ 了机器人的纯文字才进这里（私聊不用 @）；固定格式晒单哪怕 @ 了也走点赞，
口语报单被助手认出来也会退回点赞流程。配置在 `config.yaml` 的 `assistant` 段，模型和 Key 复用 `agent` 段。

### 接入 TeleAgent（星辰超级智能体）

`mcp_server.py` 把台账能力包成 10 个 MCP 工具（查战队 / 小组 / 个人 / 列单 / 名册 / 通报文字 / 导出 Excel+图 /
解析晒单 / 发通报到群 / 更新名册），TeleAgent 桌面版导入后一句话查数、出周报 PPT、发通报。
和群里 @机器人 问答共用同一段查询代码（`botcore/ledger_tools.py`），两边答案一定一致。
配置和用法见 [docs/TeleAgent接入.md](docs/TeleAgent接入.md)。

### 名册怎么更新

把活动表（带「分组」sheet：姓名 | 分组 | 战区）**直接发到群里**，机器人会：

1. 读出「分组」表，更新 `roster.json`（战区名统一成「xx战队」）
2. 把已有的单按新分组重新归队
3. 在群里回一句「名册已更新：62 人 / 6 个战队 / 31 个小组」

发别的 Excel 不会触发 —— 没有那三列表头的表一律跳过，不打扰群。
Sheet1 / Sheet2 那种成对姓名、合并单元格的排版不解析，格式一变就会读错。

### 字段写歪了怎么办（容错解析）

严格解析认「字段名 + 冒号」。有人把字段名写歪（「套餐:139」「揽收：郭静」「业务类型 新增」没冒号、顺序打乱、挤一行），
正则抓不到时，只要文字命中了 ≥2 个模板字段名，就让模型把字段抽出来，**再走同一套换算规则**记进清单。
这样记的单标黄、备注「模型解析待核对」。发给模型前先脱敏；模型只许抽文字里写了的，缺业务类型或套餐就放弃；一条消息报多单的不自动拆。
口语报单（「搞定一单199」）字段名不够，不会进这条路。配置在 `config.yaml` 的 `extract` 段。

改了解析或口径，先离线跑：

```bash
python test_parse.py                 # 内置的歪格式样例
python test_parse.py "支局 新盛 新增 139 揽收 郭静"
python test_parse.py --no-llm        # 只测严格解析，不花钱
```

### 清单里每一格怎么来

晒单模板的字段直接映射：支局 → 战区（名册优先）、业务类型、办理套餐、价值积分、是否加载 AI/云盒/智屏/FTTR、号卡数量、揽收人。

| 业务类型 | 归一化 | 备注 |
|---|---|---|
| 新增 / 新装 / 新办 | 新增 | 宽带 1；档位 ≥139 再记中高套 1、千兆 1 |
| 存量 / 续约 / 续签 / 改 / 升档 / 加装 | 存量 | 升档或续约记长续约 1；≥139 的千兆标待核对（原表里人工填的不一致） |
| 单C / 号卡 | 单C | 单号卡按「号卡数量」 |
| 套餐里带 山城卡 / 号卡 / 携转 / 异网卡 / 副卡 | **单C** | 不管业务类型填的什么，号卡不算宽带 |
| 认不出的词 | 原样记 | 标黄「业务类型待核对」 |

价值积分**以晒单里填的为准**，没填才按套餐推（新增 = 套餐价 + 附加；升档 = 差价；续签 = 0；橙分期 = 月费 − 月返）。
套餐档位、附加项、单宽/副宽、号卡/橙分期、存量叫法的完整口径见 [docs/套餐资费.md](docs/套餐资费.md)，
来自 2026-03 的入职培训课件。政策变了先改那份，再同步 `config.yaml` 的 `agent.context`。
千兆/500兆 模板里没有这个字段，只对新增且 ≥139 的记 1。
需要人工看一眼的行整行**标黄**，备注列写着缺什么。

## 十二、排查

### 静默失败的排查顺序

「群里说话没反应，但日志干干净净」是这个项目最常见、也最难猜的故障。**按下面的顺序排，不要跳步**——每一步都排掉一整类原因。

**第 1 步：跑自检**

```bash
python preflight.py
```

验凭证、机器人能力、权限。全绿说明这三类都没问题。

**第 2 步：确认机器人在群里**

```bash
python diagnose.py
```

列出机器人所在的所有群。「发布应用」和「把机器人拉进群」是两件独立的事，很多人以为发布完就自动进群了。

> 提示：如果你能在输入框里 `@` 出机器人的名字，它就一定在群里——不在群里的话 @ 列表里根本选不到。

**第 3 步：看长连接和事件帧**

把 `.env` 改成 `LOG_LEVEL=DEBUG`，重启后在群里发消息，看终端：

| 日志表现 | 结论 |
|---|---|
| 没有 `connection is OPEN` | 长连接没建起来，看 `/callback/ws/endpoint` 那一步的报错 |
| 有 `Handshake-Msg: OK`，但**只有 PING/PONG 心跳**，没有其它数据帧 | **事件根本没推过来** → 去第 4 步 |
| 有事件帧但没有「命中规则」 | 事件收到了，是匹配/过滤问题 → 用 `test_rules.py` 验关键词 |
| 有「命中规则」没有「已回复」 | 收发都通，缺 `im:message:send_as_bot` 权限 |

心跳帧长这样，认准它们（25 字节的 ping / 469 字节的 pong，每 30 秒一次）：

```
> BINARY 08 00 10 00 ... 70 69 6e 67   ← ping
< BINARY 08 9b 8d ac ... 68 00 72 00   ← pong
```

**第 4 步：检查事件订阅** ⚠️ 实测最常见的根因

开放平台 →「事件与回调」→「事件配置」，确认两件事：

1. 订阅方式是**「使用长连接接收事件」**
2. 事件列表里**确实有 `im.message.receive_v1`（接收消息）**

⚠️ **这是两个独立设置项。** 长连接握手成功只证明第 1 项配对了，不代表订阅了任何事件。事件列表是空的，连接照样能建起来、心跳照样正常，但一条消息都收不到——**日志完全看不出异常**。

**第 5 步：重新发布版本**

事件订阅和权限改完之后，必须回「版本管理与发布」**重新创建版本并发布**，改动才在线上生效。

权限能生效不代表事件订阅也生效了——如果事件是上次发布**之后**才加的，它还没上线。不确定就重发一版，成本很低。

改完记得**重启 `bot.py`**：长连接要重新握手才会拿到新的订阅配置。
